## 一、本轮最重要发现：prompt_tokens 口径歧义是一个潜伏计价 bug（A 级，本地实测）

### 1.1 三种口径真值表

「`usage.prompt_tokens` 是否已包含缓存分量」**因 provider 路径而异**，而 LLooM 的 `actual_cost`（`pricing.rs:444-449`）用 `non_cached = prompt_tokens − cached_tokens` 推导非缓存输入——这个推导只对一种口径成立：

| 口径 | prompt_tokens 构成 | LLooM 现公式结果 | 证据 |
|---|---|---|---|
| OpenAI 惯例（含 dashscope 隐式缓存） | = base + cached（cached 是子集） | ✅ 正确 | OpenAI 惯例；百炼文档：usage 字段语义需逐模型核（见 1.3） |
| Anthropic 经 litellm 1.97.0 | = base + **cache_creation** + cache_read（transform 主动加总） | ❌ **cache_creation 双重计费**：先按 p_in 计一次（混进 non_cached），再按 p_write 计一次 | `litellm/llms/anthropic/chat/transformation.py:2156-2160`（`prompt_tokens += cache_creation_input_tokens; prompt_tokens += cache_read_input_tokens`）逐字核验 |
| DeepSeek 原生字段 | litellm 构造器把 `prompt_cache_hit_tokens` 归一化为 `cached_tokens`；prompt_tokens 是否含 hit 需实测 | ⚠️ 待验证 | `litellm/types/utils.py:1740-1742`（实测构造 `Usage(prompt_cache_hit_tokens=…)` → `prompt_tokens_details.cached_tokens` 生效） |

### 1.2 Python 构造实测（A 级）

```text
Usage(prompt_tokens=1000, completion_tokens=10, cache_read_input_tokens=300, cache_creation_input_tokens=200)
→ prompt_tokens = 1000                          （构造器不自动加总；加总发生在 Anthropic transform）
→ usage.cache_creation_input_tokens = 200       （顶层属性可读 → ai_service.py:205 现有读取对 Anthropic 有效）
→ usage.cache_read_input_tokens     = 300
→ prompt_tokens_details.cached_tokens   = 300   （归一化包装）
→ prompt_tokens_details.cache_write_tokens = 200
```

**推论**：LLooM `_usage_detail`（`ai_service.py:185-215`）当前读顶层 `cache_creation_input_tokens`——对 Anthropic 路径有效；但对 **dashscope（OpenAI 兼容）路径，写 token 字段嵌在 `prompt_tokens_details.cache_creation_input_tokens`**（百炼官方文档明示），现有代码读不到 → 显式缓存的写溢价会被静默漏计（act_cost 偏低，对账时表现为「账单 > 记账」）。

### 1.3 修复设计（进 01 方案，优先级 P0 级——它影响对账正确性）

1. **UsageDetail 语义重构为显式三分量**：Python 侧（知道 provider 惯例）归一化出 `base_input_tokens / cached_tokens / cache_creation_tokens` 三字段再落库；Rust `actual_cost` 只做 `base×p_in + cached×p_read + creation×p_write` 纯乘加，**废除 `prompt_tokens − cached` 推导**。
2. **运行时 validate 断言**（风格清单第 7 条）：`base + cached + creation == prompt_tokens`（litellm 口径）不成立时报中文错误并附 provider 提示；dashscope 若实测口径不同，走 provider 白名单 + 注释记录口径依据。
3. **dashscope 口径实测步骤**：注册一个支持隐式缓存的 qwen 模型发两轮相同前缀请求 → 对照 `usage.prompt_tokens` 与 `prompt_tokens_details.cached_tokens` 的大小关系 → 若 `cached > prompt` 即为「不含」口径 → 实测一次真实账单校准（百炼控制台账单明细有「缓存命中」计费类型行，可直接对账——顺带增强 B2）。
4. **单测补充**：现有 `actual_cost_matches_litellm_formula`（`pricing.rs:912`）用的是「prompt_tokens 不含缓存」的合成形状，测不出此 bug——补 litellm Anthropic 聚合语义形状（prompt=base+read+creation）的用例。

## 二、阿里百炼上下文缓存官方文档精读（B 级 → A 级升级）

> 来源：`help.aliyun.com/zh/model-studio/context-cache`（2026-09-22 最后更新，逐字精读）。以下全部 A 级。

### 2.1 显式缓存（cache_control，OpenAI 兼容接口可用）

| 参数 | 值 |
|---|---|
| 写入价 | **输入价的 125%** |
| 命中价 | **输入价的 10%**（例外模型：qwen3.8-max / qwen3.8-flash / qwen3.8-2.4t-a95b 按控制台为准） |
| 最小前缀 | 1024 token |
| TTL | **5 分钟，命中自动刷新** |
| 标记数 | 每请求 ≤4 个；前缀回溯 ≤20 个 content block |
| 计量字段 | OpenAI 兼容：`usage.prompt_tokens_details.cache_creation_input_tokens` + `.cached_tokens`；Anthropic 兼容：`usage.cache_creation_input_tokens` / `cache_read_input_tokens` |
| 特殊语义 | tools 定义随 system 消息一起缓存（JSON 键序稳定即命中）；`usage.input_tokens` **不含**缓存分量（且后端附加约 10 个内部 token，可略高于请求构建总数——对账时的已知偏差源） |
| 支持模型 | qwen3.8-max/flash、qwen3.7-plus、deepseek-v3.2、kimi-k2.6/k2.5/k2.7-code、glm-5.1、qwen3-vl-plus/flash 等 |

### 2.2 隐式缓存（自动，不可关闭，无承诺 TTL）

- 命中价：**主力模型 = 输入价 20%**；例外表：deepseek-v4.1-flash 10%、Kimi k3 10% / k2.6 16.9% / k2.5 17.5%、GLM 5.3/5.2 25%（其余 20%）、MiniMax M2.5/M2.1 10%、外部部署（vanchin）2%-40% 浮动、qwen3.8 系非 20%。
- 最小命中前缀 1024 token；模型级+账号级隔离（不跨账号共享）；Batch（文件输入）不参与缓存折扣。
- 上报字段：`usage.prompt_tokens_details.cached_tokens`（LLooM 已读，B15 E2E 真实命中佐证）。
- **覆盖模型含 deepseek-v4.1-flash / v4-pro / v4-flash / v3.2 / v3.1 / v3 / r1**——LLooM 现注册的 deepseek-r1（dashscope）在列。

### 2.3 由官方数字推出的设计判据（D 级推导，算术自明）

**显式 vs 隐式的分界**：前缀 P + 增量 I 的一轮请求，显式成本 = 0.10P + 1.25I，隐式 ≈ 0.20P + 1.00I → **显式更省 ⇔ I < 0.4·P**（增量不足前缀 40% 时）。LLooM 多轮对话天然增量小（追加一轮），长会话中显式缓存打标大概率更省——这是新设计选项 C8 的依据（01 已增补）。

### 2.4 对既有方案的回填

- 01 §三.1 计价矩阵 DashScope 行：B 级 → **A 级**（数字全钉死）；Kimi 行补充：百炼口径 k2.6=16.9% 与 litellm 直连口径 25% 并存（不同供应商部署不同价，均真实）。
- 01 C5 TTL 门：官方显式缓存 TTL=5min 命中刷新 → 300s 保守常量**获得官方背书**；隐式「无承诺 TTL」支持悲观化处理。
- 01 C2 的 `est_write`：Anthropic 1.25× 与百炼显式 1.25× 数字巧合一致，两供应商共用逻辑。
- B2 对账增强：百炼账单明细含「缓存命中」计费类型行 + 10 内部 token 已知偏差 → `bill_reconcile.py` 可按类型行直对账。
- **新缺口（已进 01 缺口表 G8）**：dashscope 写 token 嵌套字段未读（1.1.2 推论）。

### 3.1 输出长度预测（est_out 的 related work，支撑 01 C4 / 02 Q3）

| 工作 | 要点 | 对 LLooM 的启示 |

| Uncertainty-Aware Output Length Prediction（arXiv:2604.00499） | 点估计 → 分布拟合 + 载荷自适应尾部风险分 | est_out KNN 应**报分位数（P50/P90）而非均值**；重尾分布下均值会系统性低估 |
| Entropy-Guided Length Prediction（arXiv:2602.11812） | 复用模型内部激活预测长度 | 需要模型内部信息——API 网关不可达，排除该路线（诚实边界） |
| BiCSRouter（ACL 2026 Findings） | token 长度预测作 utility-cost 路由组件 | 长度预测→路由的组件化先例，直接可引 |
| RouteBalance / "Calibrate, Then Route" | 按预测长度 LPT 排序 / 用 prompt+预测长度特征做成本感知路由 | 与 01 C4「est_out 喂 est_cost」同构 |
| OmniRouter（已有） | 长度分桶粒度显著影响路由性能 | KNN 输出做分桶而非回归的依据 |
| 输出长度自跟踪研究（arXiv:2601.01768） | LLM 自报长度不可靠 | 排除「问模型要长度」的捷径 |

### 3.2 用户记忆框架（02 Q6 的 related work 定位）

| 框架 | 机制 | 与 LLooM MVP 的关系 |
|---|---|---|
| Mem0（arXiv:2504.19413） | 生产级长期记忆：抽取-合并-更新管线 + 向量检索 | MVP 的「会话结束抽取」即其简化版；其**合并/冲突消解**（新事实覆盖旧事实）是升级路径 |
| A-MEM（NeurIPS 2025） | Zettelkasten 式记忆动态互联 | 记忆间链接，MVP 不做 |
| MemoryOS | OS 式分层记忆（短/中/长期） | 与 LLooM「会话 history + rolling summary + 长期记忆」三层结构同构，可引作设计佐证 |
| Zep / Letta(MemGPT) / LangMem | 工程化记忆服务/上下文管理 | 竞品对照 |
| Agent Memory Survey（2025-12，47 作者） | 首个统一分类法：forms（存储形态）× functions（功能）× operations | Q6 写作时用它的术语定位：「form=向量库条目，function=用户画像，operation=显式写入+会话末抽取」 |
| CloneMem | 长期记忆个性化基准 | 未来评测可选 |

**定位句（可进论文）**：LLooM 用户记忆 = 单用户场景下的最小 Mem0 形态（显式指令写入 + 低频会话末抽取 + 向量检索注入），与语义缓存物理隔离（不同 chroma collection）是其隐私设计点。

### 3.3 上下文压缩（04 preflight 层的理论支撑）

- **LLMLingua / LLMLingua-2**（Microsoft）：词级压缩最高 ~20×、性能损失小，是生产导向压缩的代表（repo ~6.6k stars，衍生出面向代码上下文的 fail-open 工程封装）。
- **抽象式压缩（Abstractive Prompt Compression）**：定期用 LLM 摘要长历史——**与 LLooM 已有的 rolling summary 完全同构**，2026 年业界把它与 prompt caching 并列为两大成本杠杆（thelec 2026-09 报道）——**LLooM 已坐在趋势上**，preflight 层只是把「摘要」从被动截断升级为主动、可配置的前置阶段。
- 2026 新工作：END 早期噪声丢弃（arXiv 2026-05）、SWEzze 代码上下文压缩（每实例省 ~13k prompt token）——代码场景压缩有直接证据。
- **对 B17 的修订**：preflight 的「预压缩」不必引压缩模型，**第一版就是 rolling summary 前移 + 工具结果摘要化**（零新依赖），LLMLingua 类留作升级选项。

### 3.4 谄媚度测量（04 心理画像特征 2 的探测设计依据）

| 工作 | 用途 |
|---|---|
| SycophancyEval（arXiv:2310.13548，Anthropic 系起点） | QnA 意见线索范式：用户先表达（可能错误的）观点再提问，测模型附和率——直接可搬进探测集 |
| SYCON-Bench | 多轮自由对话中的谄媚测量——多轮形态与 LLooM 场景更贴 |
| BrokenMath（2025） | 定理证明场景谄媚——code/数学任务专用探测的参照 |
| "Sycophancy Is Not One Thing" | 因果分离不同谄媚亚型——提醒探测集按场景分层（观点/事实/代码） |

**探测集设计修订**：谄媚度探测从「单一问卷」升级为「三场景分层（观点附和/事实纠错/代码确认）× 每场景 5-8 题」，参照 SycophancyEval QnA 范式。

## 六、仍开放的问题（诚实边界）

1. **dashscope OpenAI 兼容路径 `usage.prompt_tokens` 是否含 cached_tokens**——官方文档只钉了 native `input_tokens` 口径；需 1.3.3 的实测步骤闭合（半小时实验）。
2. DeepSeek V4 时代缓存命中折扣精确值——官方定价页迁移后未逐字核对（转述 ~2-3%），接线 DeepSeek 直连时核对。
3. LLMRouterBench HF 数据集实际可下载性与镜像（hf-mirror）——Q2 基建开工时验证。
4. Switchyard v1.0 无公开时间表——B11 维持，季度复核一次即可。
