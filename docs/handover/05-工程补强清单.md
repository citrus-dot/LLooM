## 二、密钥配置合并（手记 #21）

### 2.1 现状盘点（三渠道 + 已有防护）

| 渠道 | 载体 | 锚点 | 语义 |
|---|---|---|---|
| ① 模型级 Key | `models.api_key_env`：`sk-` 开头**字面量存 SQLite**，否则当**环境变量名** | `models.rs:92-108 ApiKeyRef::parse`、`config.rs:364-377` | 每模型独立 Key（M1 per-model key 已落地） |
| ② .env 批量注入 | `.env` 启动时注入进程环境 | `config.rs:152,330-354` | DASHSCOPE/OPENAI/ANTHROPIC 等供应商级后备 |
| ③ settings KV | `proxy_token`（立即生效）→ env 后备 | `openai_compat.rs:157-168`、`PUT /api/proxy/token server.rs:1901` | N1 代理鉴权 |
| 已有防护 | `get_config` 对 `*_API_KEY/_KEY/_TOKEN/_SECRET` 脱敏 `****+后4位`，设置页不预填 | `LLooMprogress` §五 | 掩码回传已实现 |

**诊断**：不是「混乱」，是「三渠道各有语义但缺一张统一地图」。真痛点有三个：① 新用户不知道 Key 到底该填哪（ModelsPage 直填 vs .env vs 环境变量名，三种都行但没引导）；② 排障时无法一眼回答「这个模型现在实际用的是哪把 Key、来字哪个渠道」；③ 无「这把 Key 是否有效」的一键校验。

### 2.2 方案：合并视图，不搬家（P1，2-3 天）

- **原则**：**不改变任何现有解析优先级**（SQLite 优先、env 后备是 M1 定案），只加观测与校验——「合并」指视图合并，不是存储合并。搬家反而引入迁移风险且破坏零迁移约定。
- **三件事**：
  1. **凭据清单端点** `GET /api/credentials`：聚合三源状态（模型 → 实际生效渠道[sqlite_literal|env_ref|env_fallback|none] + 掩码值 + 是否已被 get_config 消费），WebUI 设置页新增「凭据总览」卡；
  2. **Key 校验端点** `POST /api/credentials/verify`：对指定模型发一次最小成本探测（沿用 `probe.rs` ProbeBudget 状态机语义，预算内 1 次调用），返回有效/无效/欠费分类；
  3. **引导文案**：ModelsPage 填 Key 处说明三种写法等价性与优先级（「`sk-` 开头=直接存库；其他=环境变量名」——现在只有源码知道这件事）。
- **红线落实**：清单端点只出掩码（复用 get_config 脱敏函数）；校验端点不落 Key 明文日志；文档/示例不出现真实 Key 字面量。

## 三、项目理解（手记 #23，取「产品能力」解）

> 另一解读（SRTP 申报材料的「项目理解/写法」）归 06 §六处理，两不误。

### 3.1 定位：让 LLooM 「知道你在做哪个项目」，收益落在三处

① chat 提问免贴上下文；② code 任务的 est_out/难度估计更准（同项目历史样本）；③ 未来经验包检索（方向四）的检索键（需求语义 + **工作区状态** + 语言/框架）需要项目维度才能成立。

### 3.2 MVP 方案（P2，3-5 天）

1. **项目绑定**：conversations 加 `project_id`（可空）；新 `projects` 表：`(id, name, root_path, lang, framework, summary_md, created_at)`；WebUI 项目页（CRUD 简表）。
2. **摘要注入**：项目 `summary_md`（用户粘贴 README 片段或一键生成一次）注入 system prompt 头部，作为独立段（与用户记忆 02 Q6 同一注入机制，互不混叠）；**不自动扫文件系统**（隐私与性能边界），摘要内容由用户掌控。
3. **路由特征（轻量）**：`signals_json` 加 `project_lang`；code 任务难度带参考同项目历史（`model_task_score` 已是 (model,task) 粒度，读时按 project 过滤——不扩表）。
4. **不做**（明确边界）：仓库级索引/embedding 代码库（属 RAG 知识层，中期展望项）；文件树实时监听；与语义缓存的键混淆（cache_key 不含 project_id——摘要已进 system prompt，fingerprint 自然区分）。

## 四、写法改进（手记 #24，取「产品能力」解）

### 4.1 定位：写作类任务的编排模板（针对学生/科研场景）

用户高频写作场景：课程报告、论文润色、邮件/申请材料。现状「写」只是普通 chat，无专门编排。

### 4.2 方案：polish 编排模板（B19，P1-P2，2-3 天）

1. **任务类型**：`task_rules` 加 `writing` 类（正则：润色/改写/翻译/润色请求特征），进 LLM classifier 提示词；`writing` 与 `general` 分离让 `model_task_score` 开始积累写作质量数据（写作任务的最优模型常与代码任务不同）。
2. **编排模板**（复用现有 DECOMPOSE/AGGREGATE 编排框架，不新建机制）：
   ```text
   输入原文 → [诊断臂：结构/逻辑/语言三层问题清单，便宜模型]
          → [改写臂：按诊断清单改写，主路由选模型]
          → [对照臂：输出 修改对照表 + 修改理由，供用户审]
   ```
   关键点：**诊断臂与改写臂可分模型**（诊断用便宜模型足够），对照表输出格式化复用 SSE result 事件。
3. **入口**：WebUI ChatPage 模式切换（普通/polish），非破坏性（普通 chat 完全不变）。
4. **与人工润色方法论的关系**：本模板是产品功能；真正提交级润色仍按全局规则走 paper-polish 技能分工（中文 qu-ai-wei / 英文 humanizer）——两者不冲突，模板面向日常轻量场景。

// candidates_json 的新增语义（与旧 fallback 名单并存，读侧按列名区分——写侧严格、读侧宽容）

    pub name: String,
    pub provider: String,
    pub score: f64,                      // score_all 输出
    pub est_cost: f64,                   // est_cost(hit_rate, …) 现值
