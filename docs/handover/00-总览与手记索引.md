## 一、手记的两条主线（先给结论）

手记 22 个条目不是散点，收敛为两条主线 + 三个支撑面：

```text
主线 A：「路由 × 缓存 × 预算」联合优化（手记里的"综合选优"问题）
   对话上下文/缓存命中、定价方案、kv cache 推算←动态调整、综合选优、
   成本长期规划-质量稳定、缓存推算/估计、结合缓存估算token长度、综合优化求解
        ↓ 01 给工程方案，03 给数学形式化与理论叙事

主线 B：「数据 → 预测 → 评分 → 优化」闭环
   收集oracle数据集离线验证、质量预测模型、基于预测/检索、
   可用性/成本评分(分布式?)[分两维度找数据集]、上下文反馈、用户记忆、设置分类模型
        ↓ 02 给数据集与预测器方案

支撑面 C：平台化（04）—— 智能体互联协同、云端预处理/PD分离、多模态?、模型心理测试、switchyard
支撑面 D：工程补强（05）—— 密钥配置合并、项目理解、写法改进 + 决策快照等 P0 基建
支撑面 E：SRTP 包装（06）—— 打实创新点（评分系统）、上升思想理论（强化学习）
```

**一条贯穿性判断**：手记核心张力（换模型省脑力 vs 换模型丢缓存）在代码里已有「半套」解法——`est_cost(hit_rate_ewma)` 管道已存在（`router.rs:288/485` 调用，命中率来自 `db.model_cache_hit_rate(task)` 全局 EWMA，`router.rs:597`），`actual_cost` 已实现 read/write/miss 三档缓存计价（`pricing.rs:441-452`）。**剩余缺口非常精确：会话粒度命中率、前视切换代价项、cache_write 摊销、TTL 时效**。这不是从零建，是补四块——方案见 01 §五。

### D1 · 用户记忆模块（#6）做不做、什么范围

- a) **最小版（推荐）**：chroma `user_memory` collection + 显式指令写入 + 会话结束 LLM 抽取（低频）+ WebUI 管理页。约 3-5 天。依据：与语义缓存同底座（chroma 单例已封装）、不动路由评分层、隐私面小；SRTP 演示也需要「记忆」这个可讲的功能点。
- b) 完整版：加 L3 关键事实抽取（解锁 B14）、记忆置信度衰减、按项目分域。约 2 周。依据不足：当前无真实长周期使用数据支撑分域设计。
- c) 不做：等 B4/G2（agent 运行时）一并设计。代价：手记 #6 落空，且 WebUI chat 的多轮体验短板保留。

### D2 · SRTP 主创新点叙事（#25）

- a) **「缓存感知的成本-质量联合路由优化」为主（推荐）**。依据：差异化最清晰——行业先例（Dynamo/llm-d/SageMaker）全部是同模型 worker 级前缀亲和，跨模型 API 网关级的缓存协同路由没有直接先例（见 01 §三）；LLooM 已有半套机制 + 真实流量数据，可行性硬。
- b) 「校准式质量预测评分系统」为主。依据：手记点名「评分系统」；但学习型路由正处平台期（Routing Plateau 证据），评审若追问边际收益较难答。
- c) 「运行时路由（投机比较+经验包）」为主。依据：零训练创新性高；但 MVP 未落地，可行性叙述弱于 a。
- 三条可并存（a 主 + b/c 辅），见 06 §三的组合方案。
