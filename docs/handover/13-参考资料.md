
# 六、LLMRouterBench 对当前 Weak 问题最重要的研究结论

LLMRouterBench 自己的统一评估发现：

1. 没有单一模型统治所有 domain；不同模型在数学、代码等领域存在互补能力。
2. 大量 routing 方法最终效果相近。
3. Router 距离 Oracle 仍存在明显差距。
4. 其中一个主要原因就是 **model-recall failures**：某个模型是少数真正答对的模型，但 router 没有选到它。
5. 更大的 model ensemble 存在 diminishing returns，精心选择模型池比盲目增加模型更重要。

这与 LLooM 当前观察高度一致：

```text
Oracle：Weak 43.4%
LLooM：Weak 0%
```

因此下一阶段应该把问题表述为：

> **Weak recall / model recall，而不是 Weak usage ratio。**

只有 recall 提升，同时 precision 不明显下降，才属于真正的 routing improvement。citehttps://arxiv.org/abs/2601.07206

# 八、RouteLLM：最值得复用的是“threshold + cached evaluation”思路

RouteLLM 明确把 routing 形式化为：

```text
给定 query
→ 判断 weak 是否足够
→ 必要时才升级 strong
```

它公开支持：

```text
MMLU
GSM8K
MT-Bench
```

并且官方 evaluation README 指出：已有 benchmark 结果默认缓存，避免每次 evaluation 重新生成。citehttps://github.com/lm-sys/RouteLLM

RouteLLM 还提供 threshold calibration，通过 strong-model call percentage 控制质量/成本折中。官方公开结果曾报告：在 MT-Bench 上，保持约 95% GPT-4 performance 的配置可以大幅减少 GPT-4 调用；其 blog 报告的最大成本降低超过 85%。citehttps://www.lmsys.org/blog/2024-07-01-routellm/

## 对 LLooM 的直接启发

LLooM 不需要照搬其二分类 router，但应该吸收三个设计：

```text
1. “是否需要 Strong”本身就是一个合法的 routing target
2. 用 threshold / budget 控制 cost-quality tradeoff
3. benchmark evaluation 尽量使用 precomputed results
```

因此下一阶段应增加：

```text
Weak-vs-Strong threshold curve
```

作为 LLooM 的一个 sanity track。

RouterArena 当前明确把自己定义为：

```text
Evaluation-only
```

并禁止在其数据、标签上 train / fit / tune router。

它目前覆盖：

```text

```

并提供：


其 evaluation 流程还有 cached_results，可以避免不同 router 重复产生相同 model responses。citehttps://github.com/RouteWorks/RouterArena

不要把 RouterArena test 数据混进：


```text

```

这会是比 Native 自采更有说服力的第三方验证方式。

# 十、对 Weak Rescue 最有直接价值的现有研究

## 10.1 RouterDC

RouterDC 是 query-based router，核心思想就是：

> 用 query 本身决定应该组装哪个模型，而不是只依赖静态模型排名。

论文报告其在多个设置下优于单一 top model 和已有 routing 方法。citehttps://arxiv.org/abs/2409.19886

### 对 LLooM 的参考

不要马上实现 dual contrastive learning。

只吸收它的第一层思想：

```text
query → model suitability
```

这正是当前从：

```text
task_type / band
```

向：

```text
query-level model selection
```

迈进的一步。

---

## 10.2 ICL-Router

ICL-Router 特别相关的一点是：它明确把：

```text
query representation
+
model performance profile
```

结合起来预测新 query 上不同模型的表现。citehttps://arxiv.org/abs/2510.09719

### 对 LLooM 的启发

你们当前只有：

```text
model × task_type → mean quality
```

因此只能得到粗粒度判断。

下一阶段更合理的数据结构是：

```text
query embedding
        ↓
calibration neighbors
        ↓
per-model observed outcomes
        ↓
per-model predicted quality
```

这正是轻量 kNN 可以实现的东西。

---

## 10.3 RADAR

RADAR 把 routing 看作：

```text
query difficulty
×
model / budget ability
```

并用 item-response 思路学习 query difficulty 与 model ability。论文强调模型能力与题目难度之间的关系，而不是简单把模型看成一个固定分数。citehttps://arxiv.org/abs/2509.25426

### 对 LLooM 的启发

当前：

```text
band = medium
→ tier 1 不准进
```

这其实把“difficulty”硬编码成“minimum tier”。

更柔和的办法是：

```text
difficulty = evidence
ability = evidence
penalty = function(difficulty - ability)
```

因此 Soft Capability Gate 有明确的研究依据。

# 十一、最值得直接复刻思想的项目：pareto-router

这是目前搜到的、与 LLooM 下一阶段最贴近的开源工程参考。

它公开声称在 LLMRouterBench 上使用：

```text
TF-IDF
+
Ridge regression
```

对多个模型分别预测 query-level quality，然后在：

```text
quality × cost
```

上做选择。

其 README 公开的测试是 450 个 held-out queries、12 个模型，并声称在自己的实验中取得很强的 cost-quality frontier。需要强调：**这些是该项目自己的工程结果，不是同行评审论文结果，应当作为实现参考而不是外部已证实结论。**citehttps://github.com/Keyan-sm/pareto-router

真正值得 LLooM 直接借鉴的不是其 headline 数字，而是工程结构：

```text
query
 ↓
TF-IDF
 ↓
per-model quality prediction
 ↓
cost-quality selection
```

而且：

```text
core = numpy + scikit-learn
```

完全不需要再调用 LLM。

## 对 LLooM 的建议

第一版甚至不必引入 Ridge。

先做：

```text
TF-IDF
+
nearest neighbor average
```

再比较：

```text
TF-IDF + Ridge
```

这两个都可以在 calibration split 本地完成。

# 十二、R2-Router：先记住它，不要现在全做

R2-Router 当前把 routing 扩展到：

```text
model
×
output token budget
```

并使用 KNN / regression 预测不同 model-budget 的质量。其 R2-Bench 有：

```text
30,968 queries
15 LLMs
multiple output budgets
```

并报告明显的 cost-quality 改善。citehttps://arxiv.org/abs/2602.02823

### 为什么现在不做

LLooM 当前生产 router 还没有把：

```text
output budget
```

作为一等路由维度。

所以现在引入 R2-Router 会同时改：

```text
model selection
+
output length policy
```

范围太大。

正确做法是：

```text
v0.2
先解决 model recall

v0.3
再考虑 model × token budget
```

# 十三、一个非常重要的新参考：SaveRouter

2026-09 的 SaveRouter 工作专门研究：

> routing 的 supervision 本身也是成本。

它的结论是：不必为了建立 router 而完整采集 dense query × model feedback；通过 sparse supervision 也可以取得竞争力，并降低 break-even deployment volume。citehttps://arxiv.org/abs/2609.37402

这与 LLooM 当前目标完全一致：

```text
不要为了验证 routing
再付一遍 benchmark inference cost
```

虽然本阶段不需要实现 SaveRouter，但以后如果 Native Track 真需要少量新 supervision，可以参考它的原则：

```text
先找到最有信息量的 query
再让模型产生额外 outcome
```

而不是全量双跑。

# 十六、P0-3 · Weak Eligibility Audit

现在的 LLooM：

```text
Weak selection = 0%
```

必须把每道 test query 的 Weak 状态展开：

```text
weak_oracle_equivalent
weak_candidate_eligible
weak_selected
```

从而形成：

| 状态 | 意义 |
|---|---|
| Oracle Weak + not eligible | **Blocked Weak** |
| Oracle Weak + eligible + not selected | **Missed Weak** |
| Not Oracle Weak + eligible | Risky exposure |
| Not Oracle Weak + not eligible | Safe exclusion |

这一步可以直接告诉你：

```text
Weak 0%
到底是 candidate gate 问题
还是 scoring 问题。
```

# 十七、P0-4 · 三路 Ablation

只新增：

```text
Current Full
Band-only
Quality+Cost without hard Weak gate
```

### 结果判断

如果：

```text
Quality+Cost without hard gate
→ Weak share 大幅上升
→ quality 基本不掉
```

则说明：

```text
Capability gate = 主要瓶颈
```

如果：

```text
Weak 已 eligible
但仍几乎不选
```

说明：

```text
Quality estimation = 主要瓶颈
```

# 十八、P0-5 · Soft Gate Sweep

第一轮不要改生产逻辑。

增加 benchmark policy：

```text
soft_gate_penalty
∈
{0, .05, .10, .15, .20}
```

只影响 benchmark variant。

然后观察：

```text
Weak Recall
Weak Precision
Cost Saving
Quality Retention
Mean Oracle Regret
```

### 预期实验结构

```text
Hard Gate
   ↓
Soft Gate 0
   ↓
Soft Gate .05
   ↓
Soft Gate .10
   ↓
Soft Gate .15
   ↓
Soft Gate .20
```

如果只需要很小 penalty 就能让 Weak recall 明显上升，这是一个很强的改进信号。

# 二十、P1 · CPU-only Query Router

只有在 Soft Gate 明显有效、但 Weak Recall 仍低时才进入。

推荐最小实现：

```text
TF-IDF
+
Top-K cosine neighbors
+
per-model score average
```

### 训练

```text
calibration only
```

### 输入

```text
prompt
```

### 输出

```text
predicted_quality[model]
```

然后将预测结果转成 LLooM 可消费的：

```text
quality_override
```

或者 benchmark-only suitability signal。

### 第二级

再增加：

```text
TF-IDF + Ridge
```

参考 `pareto-router` 的实现思路。citehttps://github.com/Keyan-sm/pareto-router

# 二十一、P1 · Task-only / kNN / Full 对照

最后形成：

```text
Task-only
kNN
Full LLooM
Oracle
```

如果：

```text
kNN >> Task-only
```

则说明真正缺的是：

```text
query-level suitability
```

如果：

```text
Full LLooM ≈ Task-only
```

则说明当前 router 实际上还没有利用 query-level 信息。

# 二十二、P1 · Matched Random

当前 Random 的成本不同，不能直接证明 content-aware routing 的价值。

新增：

```text
Cost-Matched Random
Strong-Share-Matched Random
```

### Cost-Matched Random

要求：

```text
E[C_random] ≈ C_LLooM
```

### Strong-Share-Matched Random

要求：

```text
P(Random=Strong)
≈
P(LLooM=Strong)
```

然后比较：

```text
Quality_LLooM
vs
Quality_random_matched
```

这会把“LLooM 只是调了模型比例”与“LLooM 真正在看 query”区分开。

# 二十三、P1 · Error Taxonomy 升级版

建议最终每个 sample 都有：

```json
{
  "selected_model": "...",
  "oracle_equivalent_models": ["..."],
  "selected_score": 1.0,
  "oracle_score": 1.0,
  "regret": 0.0,
  "weak_eligible": true,
  "weak_oracle_equivalent": true,
  "weak_selected": false,
  "error_class": "missed_downgrade"
}
```

error class 最终统一为：

```text
correct_optimal
correct_downgrade
correct_mid
correct_escalation
benign_overrouting
missed_downgrade
under_routing
missed_escalation
```

这样以后任何 Router variant 都能在同一维度比较。

# 二十四、真正值得快速尝试的 Router 改进顺序

不要一次把所有研究方法都塞进 LLooM。

推荐：

```text
                Current LLooM
                     │
                     ▼
               Weak Eligibility
                     │
          ┌──────────┴──────────┐
          ▼                     ▼
       Blocked              Eligible
          │                     │
          ▼                     ▼
      Soft Gate             Quality
                              │
                              ▼
                         Query-level
                         suitability
                              │
                       ┌──────┴──────┐
                       ▼             ▼
                      kNN          Ridge
```

也就是说：

> **先解决 Weak 有没有资格竞争，再解决 Weak 为什么输给其它模型。**

这比一开始训练复杂 router 快很多。

# 二十五、Model Pool Search 推荐输出

不要只输出一个三模型池。

建议自动生成：

```text
pool_candidates.json
```

每个 candidate：

```json
{
  "weak": "...",
  "mid": "...",
  "strong": "...",
  "weak_mean_quality": 0.0,
  "mid_mean_quality": 0.0,
  "strong_mean_quality": 0.0,
  "weak_oracle_share": 0.0,
  "mid_oracle_share": 0.0,
  "strong_oracle_share": 0.0,
  "oracle_gain": 0.0,
  "cheap_safe": 0.0,
  "winner_entropy": 0.0,
  "cost_ratio": 0.0,
  "screen_score": 0.0
}
```

最终至少保留三种：

```text
max_cost_leverage
max_weak_opportunity
max_diversity
```

然后在 test split **冻结一次性确定最终池**。

# 二十六、一个更合理的 screening score

第一版可以继续使用简单线性排序：

```text
PoolScore =
    0.30 × normalized_oracle_gain
  + 0.25 × weak_oracle_share
  + 0.20 × cheap_safe
  + 0.15 × winner_entropy
  + 0.10 × normalized_cost_ratio
```

这里的 `PoolScore`：

```text
只用于 screening
```

不进入 production router。

### 为什么加 `weak_oracle_share`

因为下一阶段不是一般的“多模型 routing”，而是有一个非常具体的研究问题：

```text
让低成本模型真正参与 routing。
```

因此如果一个 pool 的 Weak：

```text
oracle_share ≈ 0
```

即使其它指标很好，也不值得拿来做 Weak rescue。

# 三十一、何时可以宣布“Weak rescue 成功”

不能只看：

```text
Weak selection rate ↑
```

必须同时：

```text
Weak Recall ↑
AND
Weak Precision 高
AND
Quality Retention 不明显下降
AND
Cost Saving ↑
AND
LLooM > cost-matched random
```

一个理想结果形态是：

```text
Current
Weak Recall      ~0%
Saving           36.1%
Retention        92.9%

Weak-rescue v1
Weak Recall      ↑↑
Saving           ↑
Retention        ≈ / ↑
```

而不是：

```text
Weak Recall      ↑↑
Weak Precision   ↓↓↓
Quality          ↓↓↓
```

后者不是优化。

# 三十三、建议形成的最终研究叙事

如果下一阶段顺利，最漂亮的故事不是：

> “我们把 Weak 选择率从 0 调到 35%。”

而是：

```text
1. Public frozen outcomes show strong model complementarity
        ↓
2. Oracle reveals large low-cost opportunity
        ↓
3. Current LLooM captures part of quality-cost tradeoff
        ↓
4. Error taxonomy discovers Weak is structurally blocked / under-recalled
        ↓
5. Soft gate restores candidate eligibility
        ↓
6. Lightweight query-level predictor recovers more model-specific wins
        ↓
7. Cost-matched baselines confirm this is not merely model-share tuning
        ↓
8. Cross-benchmark evaluation confirms generality
```

这样最终能把“为什么 routing 有价值”“LLooM 当前哪里不够”“我们如何改进”“改进是否真的有效”四件事连起来。

# 三十七、最终建议

当前最有价值的行动不是继续扩展文档，也不是立刻花钱跑 Native，而是：

```text
LLMRouterBench frozen outcomes
        ↓
13-model pool search
        ↓
找出真正适合做 Weak 的低成本模型
        ↓
Weak Eligibility Audit
        ↓
Soft Gate
        ↓
TF-IDF / kNN / Ridge
        ↓
matched baseline
        ↓
cross-benchmark replay
```

**这条路径完全可以在零 API 成本下完成第一轮，而且比继续微调当前 `λ` 更有信息量。**

尤其值得立即执行的是：

> **“全模型池搜索 + Weak Eligibility Audit”**。

如果结果证明大量 query 的最佳低成本模型根本不是当前的 Mistral-7B，而是某个新的、更强但仍然便宜的模型，那么甚至不需要复杂地修改 routing 算法，**单纯替换 / 重定义 Weak 就可能先得到一次明显的 quality-cost 跃迁。**

如果模型池换掉后 Weak 仍然 0%，那么就可以非常有把握地把问题定位为：

```text
query-level model recall
```

此时直接进入 TF-IDF / kNN / Ridge，是成本最低、解释最清楚的下一步。
