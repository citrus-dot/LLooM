### 2.4 协作机制（沿用并显式化既有纪律）

1. **评审铁律**：任何人触碰 `router.rs/pricing.rs/signals.rs/db.rs` 的 PR 必须甲 review；乙丙在各自领地内互相 review 即可。
2. **变更登记**：settings 开关（01 §5.2 总表）与 DB 迁移（01 §5.3 / 05 附录）是**共享登记簿**——谁加键谁登记，禁止绕过总表新增开关。
3. **验收统一**：每工作包完成 = `cargo build/test` 全绿 + 对应 gate（01 §5.5/5.6、02 §5.3）通过 + 影子数据存档；三人共用 `aiq_replay.py` 曲线做对比汇报。
4. **提交纪律**：conventional commits + bullet 说明机制落点（仓库既有惯例）；开工前 `git status` 核对（防并行改动互卷）。
5. **每周对齐一次**（15 分钟）：只看三样——关键路径状态、gate 通过率、影子曲线异常。

### 2.5 风险与可调整点

| 风险 | 缓解 |
|---|---|
| 甲是单点（bus factor） | 决策层独占是红线要求而非信任问题；乙丙各维护一份「领地 README」（端点/管线入口清单），甲的方案文档（00-07）本身就是交接面 |
| 乙的校准/评测是论文关键路径，若 S4 未过 gate | V0 闸门本来就允许不过（回落 EWMA）；论文叙事用 Q2 离线验证兜底（公开集结论不依赖本地校准） |
| C11（丙）延误卡住 C1/C2（甲） | C11 拆两段：S1 先交 `derive_session_key` 纯函数+单测（甲可先用 WebUI 路径联调），S2 再接 /v1 |
| 三人技能与画像不符 | §2.2 按工作包粒度可整体平移（如丙↔乙互换 Python/前端领地），只要守「决策层单人独占」一条 |
| δ 触发项挤占主线 | 触发项一律用 04 §八开工包的 72h 盒子限定，超盒即记台账下周期 |

**取决于你的追问点（不影响计划成型，但影响排布）**：①三人是否都含你本人？（本计划按「甲=你」排布；若你只做甲的主线评审，S1-S2 的甲任务需再拆）②队友的 Rust/Python 水平？（决定丙能否分担 E1 这类 Rust 小项）③周期锚定校历（SRTP T0）还是自然周？（影响 S5 论文时点与中期检查对齐）。
