# 01 · 缓存感知定价与路由协同（方案书）

> 手记覆盖条目：`对话上下文/缓存命中`、`定价方案（kv /prompt cache缓存命中节约、成本预估）`、`kv cache记录/推算消耗 <- 动态调整`、`（综合选优问题）`、`成本长期规划-质量稳定`、`缓存推算/估计`、`结合缓存估算token长度`。
> 手记原话（核心张力，逐字）：「同一个用户的请求，一方面：简单问题给到简单模型，可以节省费用提高性能；另一方面：不同的请求给到不同模型，会导致缓存不命中，又会使费用上升。所以这里边有个综合选优的问题」。
> 代码基线 `412ea10` · 性质：方案书，不动代码。

## 一、问题重述：这是两个目标的联合优化，不是一个开关

把「综合选优」写成精确形式（后续所有方案都为它服务）：

```text
对请求 q（属于会话 s，会话此前的主模型为 m_prev）：

选 m* = argmax_m  P̂(ok | q, m) · V_q
                  − ÊC(m, q, s)            ← 期望账单成本（缓存感知）
                  − μ · SL(m_prev → m, s)  ← 切换损失（丢缓存的前视代价）
                  − λ1 · latency(m)        ← 延迟项
                  + 探索项 UCB(m)           ← 不确定性补偿
```

其中**期望账单成本**不是价目表查表，而是：

```text
ÊC(m, q, s) = est_in(m, q, s) · [ (1−ĥ(m,s)) · p_in(m) + ĥ(m,s) · p_read(m) ]
            + est_write(m, s) · p_write(m)          ← 仅 Anthropic 类显式写溢价供应商
            + est_out(m, q) · p_out(m)
```

三个量决定了这套东西成不成立，也正是手记后三行指的方向：

| 量 | 含义 | 手记对应句 | 现状 |
|---|---|---|---|
| `ĥ(m,s)` | 期望缓存命中率（模型 × 会话 × 前缀稳定性 × TTL） | `缓存推算/估计`、`kv cache记录/推算消耗 <- 动态调整` | **task 级全局 EWMA 已有，会话级没有** |
| `est_in / est_out` | 输入/输出 token 长度估计 | `结合缓存估算token长度` | est_out KNN 设计已有未开工；est_in 现为粗估 |
| `SL(·)` | 切换损失 = 前缀 token 数 × (p_in − p_read) × (1−ĥ_new) | `综合选优问题` | **完全没有**（sticky_bonus 只是后视加分，见 §二.3） |

**一句话诊断：LLooM 已经把「缓存贵的证据」记下来了（cached_tokens 全链路、三档计价、task 级命中率 EWMA），但评分时只会「回头看」（谁历史上省过钱加分），不会「向前算」（现在换模型要亏多少）。01 的全部工作就是把「向前算」补上。**

**对 LLooM 的三个直接推论**：

1. **写溢价只有 Anthropic（与 Gemini 显式）有**——G2 缺口只影响部分供应商，实现时按 `cache_write_cost.is_some()` 分支，与 sticky_bonus 现有分支习惯一致。
2. **TTL 全行业都是分钟级**——「会话空闲超窗则命中率归零」的近似是安全的：把 TTL 统一保守取 5 分钟（Anthropic 5min 档 / OpenAI 10min 取小），超过即视为 `ĥ→0`，宁 pessimistic 不 optimistic。
3. **计量字段供应商各异**——litellm 会归一化到 `Usage` 对象，但 `cache_read_input_tokens` 是否总经 `prompt_tokens_details.cached_tokens` 透传**需逐 provider 实测**；缺口按现有 `field_missing` 记账机制兜底，不告警只进校准。

### 3.2 行业与学术先例：空白点在哪（SRTP 差异化叙事的证据，也在 06 §三引用）

| 先例 | 层级 | 与 LLooM 的差异 |
|---|---|---|
| NVIDIA Dynamo KV Router（K8s，~2× TTFT 收益，Baseten 实测）；llm-d Endpoint Picker；SageMaker 前缀感知路由（中位 TTFT −77%）；GKE Inference Gateway | **同模型多副本/worker 间**选路由：把请求发给「已经持有该前缀 KV 的那个 worker」 | 选的是部署位置，模型不变、缓存价不变——没有「跨模型丢缓存」问题 |
| FATE（arXiv:2605.07238, 2026）：异构 LLM 工作流调度，未来状态感知（CP-SAT 前沿规划器，显式保留 future state，makespan −32.5% vs RoundRobin） | **调度层**：切换代价/迁移代价进入调度目标 | 最接近的学术先例，但在 GPU 集群调度语境，不在 API 网关/模型选择语境 |
| Cascadia（级联服务，显式切换代价因子 ε）、Talaria（serverless 会话感知）、OServe（把 switching cost 当异构路由中心问题） | 系统层级联/会话 | 支撑「切换代价该进目标函数」这一命题，均非 API 网关跨模型计费语境 |
| SGLang cache-aware LB / vLLM prefix caching | 引擎内部 | 不可达（LLooM 是 API 侧，红线：不改推理引擎） |

**结论（可信、可写进论文 related work）**：「跨模型选择的缓存协同路由」在 API 网关层是空白——行业做了同模型的部署级亲和，学术做了集群调度级未来状态；**用 API 计价差异（p_in vs p_read vs p_write）把缓存损失折算成钱并进模型选择目标，未见直接先例**。这是手记「综合选优」问题的学术化定位。

### 3.3 计价不变量与已知坑（第二轮调研发现，`pricing.rs` 的正确性前提）

> 详见 07 §一。核心：**`usage.prompt_tokens` 是否已含缓存分量是 provider 路径相关的口径**——OpenAI 惯例含 cached；Anthropic 经 litellm 1.97.0 被主动加总 read+creation（`transformation.py:2156-2160`）；百炼官方明示 `input_tokens` 不含缓存分量（后端附加 ~10 内部 token）。LLooM `actual_cost` 的 `non_cached = prompt_tokens − cached` 推导只对第一种口径成立，且单测合成形状测不出此问题（`pricing.rs:912` 用例的 prompt_tokens 不含缓存）。

**修复设计（对账正确性，P0 级）**：① Python 侧按 provider 归一化出显式三分量 `base_input_tokens / cached_tokens / cache_creation_tokens` 落库，Rust 废除推导式、只做三段纯乘加；② 运行时 validate 断言 `base+cached+creation == prompt_tokens`，不成立报中文错误附 provider 提示（风格清单第 7 条）；③ dashscope 口径实测半小时闭合（同前缀两轮请求对照 + 百炼账单「缓存命中」类型行直接对账，顺带增强 B2）；④ 补 litellm Anthropic 聚合语义形状的单测。

## 四、方案设计（C1-C6，全部 settings 三态门控 + 一键回退）

> 命名沿用 C 前缀（对应 00 §六.2 的 C8-C11 入账建议）。每项给机制、落点、工作量、验收。

### C1 会话级命中率 ĥ(m, s)（P1 核心）

- **机制**：`hit_of(input, m)` 的取值优先级改为四级：
  ① 会话×模型 EWMA（`conversation_cache_avg` 已有，扩展为按模型分组）当会话内该模型有 ≥2 次命中记录；
  ② 否则 (模型×任务) 全局 EWMA（现状值）；
  ③ 修正因子：`ĥ ← ĥ × prefix_stability(s)`（信号已有）× TTL 时效门（C5）；
  ④ 全部缺失时回 `field_missing` 语义的默认值 0.0（保守，等价于现在行为）。
- **落点**：`router.rs:588-598`（hit_rate 组装处）+ `db.rs conversation_cache_avg`（加 `model_name` 分组参数，SQL 一行）。
- **工作量**：1-2 天 + 单测。**回退**：settings `cache_aware_session_hit=off` 即回全局 EWMA。

### C2 前视切换代价 SL 项（P1 核心，「综合选优」的直接兑现）

- **机制**：`score_all`（`router.rs:477-528`）加一项，替换/融合 sticky_bonus 的语义：

```text
SL(m_prev → m) = est_prefix_tokens(s) × (p_in(m) − p_read(m)) × (1 − ĥ(m, s))
贡献到得分：−μ · SL / norm_cost基线        （μ 与 cost_weight 同源，避免第二个手调权重）
```

  - `est_prefix_tokens(s)` = 会话当前上下文 token 数（`CONTEXT_BUDGET` 24000 封顶，服务端已算过 history+summary，直接取）；
  - 留在 `m_prev` 时 SL=0；这正是 sticky_bonus 想表达而没表达对的「切换是成本」——**用钱计价替代拍脑袋的 cap 0.25 加分**，顺带消灭一个手调量（符合「手调量→有原则的估计量」总方针）；
  - sticky_bonus 保留为「无会话上下文时的降级近似」，或直接退役（建议后者，减少两套逻辑）。
- **量级 sanity check**（用 litellm 实测价）：24k 前缀会话中从 deepseek-chat（0.1× 命中）切走再切回：单次损失 = 24000 × (2.8e-7 − 2.8e-8) ≈ **$0.006**；同规模前缀换 Anthropic sonnet-4：24000 × 2.7e-6 ≈ **$0.065/次**——量级合理：短闲聊切换代价可忽略（SL≈0，路由自由度完全留给质量项），长上下文会话切换代价显著（SL 主导，天然粘性）。**这个「代价随前缀长度自适应」的性质本身就是设计卖点**：不需要人为判断「该不该粘」，钱自己会说话。
- **工作量**：2-3 天 + 影子对比。**验收**：影子双跑观察「会话内切模率」下降幅度与「成本/质量」配对 Δ（B3 配对判据）；**缓存回归检查（M4）**：live 后命中率与 saved_cost 不回归（阈值 −5%）。

### C3 est_cost 补 cache_write 期望溢价（P1）

- **机制**：`est_cost`（`pricing.rs:481`）加一项 `est_write × p_write × (1 − h_write_amortized)`，其中 `h_write_amortized` = 会话内预计复用次数摊销（简化：Anthropic 5min TTL 内每轮重写一次，取 `est_write = est_in × (1−ĥ)`）。输出侧仍按顶层价。
- **落点**：`pricing.rs:481-490` 单函数 + 既有单测补 case。**工作量**：0.5-1 天。
- **诚实边界**：摊销假设是 D 级工程自创，注释写明，不归因论文。

### C4 est_out 长度预测 × 缓存耦合（P1，研究文档 P0 项的缓存补全）

- **机制**：est_out KNN（usage_records 全量 token 列，KNN + (模型×任务) 校准系数，MAPE 相对 750 基线收窄 ≥30%——目标沿用研究文档）产出的 est_out 直接喂 `est_cost`；est_in 同法取「同会话上轮 prompt_tokens 的 EWMA + 本轮增量」，不再粗估。
- **为什么和缓存耦合**：`est_in` 的缓存前折扣依赖 `ĥ`，`ĥ` 的输入之一是前缀长度——三个估计量共享同一套检索基建，一次建好。
- **落点**：`server.rs` plan 组装处 + Python 微服务可选 ONNX 化（红线：Rust 单一决策真源，Python 只出数值）。

### C5 TTL 时效门（P1）

- **机制**：会话 `last_message_at` 距今 > TTL_PROVIDER（保守常量 300s，settings 可调）时 `ĥ ← 0`。会话时间戳已有（conversations 表），纯查表判断。
- **工作量**：0.5 天。**注意**：`field_missing` 供应商（无缓存计量）不受影响，仍走原路径。

### C6 代理路径（/v1）缓存接入（P2，N1 流量增长后的收益兑现）

- **机制**：① 请求头 `X-LLooM-Session`（四级优先级方案沿用研究文档 D3：标准 `user` 字段 > `X-LLooM-Session` > api_key 哈希×首 turn 指纹 > fail-open）；② 会话键落 `routing_decisions`，`conversation_id` 不再恒 None；③ `ChatCacheCtx` opt-in 接入 `openai_compat`；④ 命中率 EWMA 开始学习代理流量。
- **落点**：`openai_compat.rs:280-356` 区段；四级键逻辑建议做成独立纯函数放 `router.rs` 或新 `session.rs`（可单测）。
- **工作量**：2-3 天。**风险**：代理流量无 lloom 会话语义，缓存命名空间必须与会话键绑定隔离（沿用 `cache_key = hash(model + system_id + fingerprint + session_key)` 决策，见 `LLooMprogress` §二）。

### C7 成本长期规划-质量稳定（P2，手记 #7）

- **机制**：① 执行器补全——`budgets.action_on_exceed` 接线：滑窗消耗率超 `soft_limit_ratio` 时切 `throttle`、达 `max_budget` 时执行 action（protect 档语义已有，`router.rs:298`）；② 月度对账纳入 `cache_saved_cost` 列（bill_reconcile 报表加一行「缓存节省」）；③ 质量稳定护栏：任何缓存相关 live 切换前后跑 B3 配对验收 + M4 缓存回归。
- **落点**：`db.rs` budgets 消费处（`server.rs` 预算联动段）+ `scripts/bill_reconcile.py`。

### C8 显式缓存自动打标（cache_control 注入，P2，第二轮新增）

- **机制**：对支持显式缓存且走 OpenAI 兼容 dashscope 路径的模型，ai_service 组装请求时自动在稳定的 system prompt（+ tools 定义）上打 `cache_control` 标记——litellm 对 dashscope 不剥该字段（`llms/dashscope/chat/transformation.py:15-23` override 实证），SDK 层可行。
- **决策判据（D 级推导，官方数字算术）**：前缀 P + 增量 I，显式 = 0.10P+1.25I vs 隐式 ≈ 0.20P+1.00I → **I < 0.4·P 时显式更省**。LLooM 多轮会话增量占比天然小，长会话大概率满足；实现为逐请求判断（`本轮增量 tokens / 会话前缀 tokens`），满足才打标。
- **落点**：`ai_service.py` 请求组装处 + settings 开关 `explicit_cache_marking`（默认 off）；打标决策记入 `signals_json` 便于归因。
- **工作量**：1-2 天。**风险**：与隐式缓存互斥语义（同一请求二选一）；≤4 标记、≤20 block 限制对 LLooM 的 [summary+history] 结构天然满足。

## 六、风险登记

| 风险 | 缓解 |
|---|---|
| SL 项权重 μ 引入新手调量 | μ 与 cost_weight 同源同尺度（都是 USD 计价后归一），且 SL 是真实价差计算而非拍脑袋常数；影子期观察 μ=1 的默认值即可 |
| `ĥ` 高估导致错误粘住贵模型 | TTL 门悲观化 + `field_missing` 归零 + 命中率样本 <2 次不启用会话级值 |
| 百炼缓存折扣因子录入错误（10 倍量纲前科，`LLooMprogress` §七.2） | 沿用 `[1e-9,1e-3] USD/token` 写入断言 + 周度价格漂移哨兵（差额 >5% 告警） |
| 代理路径缓存污染 | 缓存键绑定 session_key；opt-in 灰度；probe/shadow 路径维持传 None（现状已如此） |
| 数据稀疏：单用户会话样本少 | C1 的四级降级保证「有全局值就至少不比现在差」；会话级值只在 ≥2 样本时启用 |
